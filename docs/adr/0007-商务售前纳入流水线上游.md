# ADR 0007: 商务售前纳入流水线上游

- **日期**: 2026-08-02
- **状态**: 已采纳

## 背景

`delivery-flow` 原本把商务/售前（商机、客户、预算、合同范围、工期）明确画在流水线**范围之外**。结果是**断层**：商务产出靠人肉转述进 PRD，商机到验收之间断成两截，无可追溯衔接。

BMAD 是内部研发框架，天然没有乙方↔客户环节——这正是当初补 client-gate/acceptance-gate 的理由。同样地，售前编排、签约关卡、CRM 同步这三块能力也不在现有生态内。

## 决策

把**售前阶段**（商机确认 → 方案/报价 → 签约 → 立项移交）纳入流水线上游，遵循三条硬约束：不造轮子、不开发系统、与产品流程无缝对接。

1. **覆盖范围＝售前聚焦**：只补商机→签约→立项这段乙方售前主线；细粒度线索获取/自动化留飞书人工，不做完整销售漏斗自动化。
2. **衔接机制＝Trace 全链路贯穿**：根 ID = 商机编号 `OPP-{YYYY}-{NNN}`，由 `delivery-presales` 在商机确认时生成，赢单后即项目交付编号。落点：商机表(飞书) → 报价单 → 立项包 → `SPEC.md` 头部引用行 → `project-progress.yaml` 顶层 `trace_id`。下游 Story/映射/评测/验收已锚定 SPEC，故传递闭合。
3. **数据承载＝飞书多维表格**：复用 `lark-base` 建商机表/客户表/合同表 + 「阶段状态」单选字段（销售漏斗），契合 ADR 0002「飞书作执行 SSOT」。

新增三个 `delivery-*` skill（纯 Markdown 流程，延续 ADR 0001 的分层哲学）：

1. **delivery-presales**：售前编排/商机路由，镜像 onboarding 路由范式，分析全部委托 BMAD；
2. **delivery-deal-gate**：合同签约关卡，镜像 client-gate 三入口结构，放行产出**立项包**把商务基线喂给 SPEC/project-context；
3. **delivery-crm-sync**：商机/客户/合同 → 飞书多维表格 SSOT，镜像 feishu-sync 的幂等映射范式。

宏观阶段前缀新增 `opportunity`/`proposal`/`deal_gate` 三个（对称 `client_gate`/`acceptance_gate` 命名）；商务谈判 + 细粒度漏斗状态不进宏观阶段，作为飞书商机表单选字段——复刻 `sprint-status`(细) vs `project-progress`(宏) 的分层设计。

## 为何不引入外部 CRM 系统

引入独立 CRM 会违背「不开发系统」约束，制造出与交付流水线并列的第二个系统，反而加剧断层。售前所需能力现有生态已基本齐备（BMAD 做分析、lark-base 做数据、关卡范式做把关），真正缺的只是「乙方售前编排 + 签约关卡 + CRM 同步」这层薄编排——自建 3 个 skill 是既定哲学的延续，不是新系统。

## 后果

- 正面：商机→SPEC→Story→飞书→评测→验收串成一条可追溯链，商务与交付不再断层；
- 正面：立项包成为商务→交付的正式接缝，PM 起需求读立项包而非人肉转述；
- 正面：`core.py` 唯一代码改动是纯追加（三阶段 + 上游 Trace 延伸），运行时仍只读；
- 代价：售前团队需按约定生成商机编号并维护飞书 CRM，靠自觉不靠技术锁（同 ADR 0005）；
- 代价：Trace 根一旦生成即不可变，若商机编号编错需人工订正 SPEC 头部与 progress。
