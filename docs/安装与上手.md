# 安装与上手 — delivery-flow 插件

> 让新团队从零装好、跑通 delivery-flow，并理解"团队级怎么用"。
>
> **目标读者**：PM / 项目经理 / 流程负责人（非所有成员都需要安装本插件）。

---

## Part 1 — 安装（分步）

本插件是 Claude Code / ZCode 的工作流规范插件，依赖两个研发基座和飞书技能。安装顺序：**基座 → 插件 → 项目配置 → 真实项目验证**。插件本身提供 Markdown Skill、模板和角色路由，不包含飞书 API、评测 runner 或自动门禁执行器。

### 1.1 装基座 BMAD-METHOD v6

BMAD 作为产品与规划方法论基座，提供分析研究、SPEC、PRD、UX、架构、技术就绪检查、Story 拆解和 project-context 生成能力。delivery-flow 不重复实现这些能力。

```bash
npx bmad-method install
```

> ⚠️ **验证说明**：此命令形式取自 BMAD 公开文档，**尚未在实际空白项目验证过**。若执行失败，请查阅 BMAD-METHOD 官方仓库获取最新安装方式。安装成功后项目根会生成 `_bmad/` 目录。

### 1.2 装基座 Superpowers（研发内功）

Superpowers 提供 TDD、系统化调试、写计划、验证等研发内功，由 `obra/superpowers` 提供。

```bash
# 通过 Claude Code / ZCode 的插件市场安装
# 在项目 .claude-plugin/marketplace.json 中添加：
# { "name": "superpowers", "source": "obra/superpowers" }
```

> 若使用 ZCode，也可通过 `/.marketplace` 或技能管理界面搜索安装。

### 1.3 装 delivery-flow 插件

本插件通过 marketplace 机制加载。在消费方项目中按以下步骤配置：

1. 在消费方项目根 `.claude-plugin/marketplace.json` 的 `plugins` 数组中，加一条指向 delivery-flow 仓库的条目，例如：

```json
{
  "name": "delivery-flow",
  "source": "<delivery-flow 仓库路径或 marketplace 名称>",
  "description": "交付型敏捷 AI 研发工作流"
}
```

> 若 marketplace 尚未包含 delivery-flow，可先通过 marketplace 源配置引入（将 delivery-flow 的仓库路径加入 `marketplaces` 数组），再在 `plugins` 中引用。

2. 重新加载 Claude Code / ZCode 配置，delivery-flow 即可识别并使用。

### 1.4 建 project-context.md

在项目根创建 `project-context.md`（**实例层配置文件**，放项目特定约束）：

**方式 A**：跑 BMAD 交互生成
```bash
bmad-generate-project-context
```

**方式 B**：复制模板手动改
从 `templates/project-context模板.md` 复制到项目根，改名为 `project-context.md`，填入项目名、预算红线、技术栈、性能验收线、AI 评测阈值等。

> `project-context.md` 是 AI Agent 的"宪法级"注入文件——预算、技术红线、性能验收线、风险防线全部写在这里，消费方项目必须存在。

### 1.5 触发 onboarding，开始引导

在 Claude Code / ZCode 对话中说 **"我该做什么？"**，或显式调用 delivery-onboarding skill（在对话中描述你的角色和当前阶段）。

Onboarding 会自动检测：
- 基座是否就位（BMAD + Superpowers）
- project-context.md 是否存在
- 识别你的角色（产品经理/项目经理/研发/AI 工程师）
- 定位当前在流水线哪个阶段
- 路由到对应 skill

## Part 2 — 谁驱动 + 如何引导角色

### 核心原则

> **onboarding 是引导入口，通常由 PM / 流程负责人驱动**，不是每个团队成员各自开 Claude Code 跑一次。一人用 onboarding 驱动 → 产出飞书任务 / 客户确认件 → 通过飞书/文档分发 → 团队从飞书领活。

### 角色 → 工作依据 → 主责阶段 → 调用

| 角色 | 工作依据 | 主责阶段 | 调用的 skill / 工具 |
|---|---|---|---|
| **产品经理** | 需求原文 + `project-context.md`（红线/约束） | 分析立项 → SPEC / PRD → UX | BMAD brainstorming / research / product-brief / prfaq / spec / prd / ux |
| **UX / 原型负责人** | SPEC + PRD + `project-context.md` | 视觉与交互设计 → HTML 演示原型 | `bmad-ux`、`delivery-prototype-html` |
| **项目经理** | SPEC + 客户确认记录 + readiness 报告 | 客户确认 → 方案就绪 → 拆任务 → 跟进 → 验收 | `delivery-client-gate`、`bmad-create-epics-and-stories`、`delivery-feishu-sync`、`delivery-sprint-sync`、`delivery-acceptance-gate` |
| **架构师 / 技术 Lead** | SPEC + PRD + `project-context.md` | 架构设计 → 技术就绪检查 | `bmad-architecture`、`bmad-check-implementation-readiness` |
| **研发工程师** | 飞书子任务 + Story AC + SPEC 引用 | 敏捷研发 | 从飞书领任务 → Superpowers（TDD/调试/验证）→ 改飞书阶段状态 |
| **AI 工程师** | Stories/AC + 评测阈值 | AI 评测 | `delivery-eval-loop` |
| **QA** | Story AC + SPEC Success signal + 评测报告 | 测试与回归 | 人工测试、`bmad-qa-generate-e2e-tests` |

> `delivery-sprint-sync` 只从飞书单向刷新本地状态镜像，不是第二个状态写端。

### 现实模式：一人驱动，全员跟飞书

```
PM/项目经理 驱动 onboarding
    ↓
产出客户确认记录 / 飞书任务
    ↓
通过飞书/文档分发给团队
    ↓
研发从飞书领活 → 改状态 → PM 跟飞书看进度
```

- 团队其他人**不需要**装 Claude Code / ZCode，也不需要触发 onboarding。
- 他们从飞书领任务、改阶段状态即可参与。
- 项目经理通过飞书看板一眼看全局。

## Part 3 — 完整走一遍（示例流程）

以下展示一个典型 AI 应用项目从需求接入到验收的全流程，每步标注调用的 skill 和产出物。

```
Step 0   需求接入与分析立项
          ↓  BMAD brainstorming / research / product-brief / prfaq
          ↓  产出：产品 Brief / PRFAQ

Step 1   产品规划
          ↓  bmad-spec / bmad-prd / bmad-ux
          ↓  产出：SPEC.md + PRD + DESIGN.md / EXPERIENCE.md + 线框

Step 2   HTML 交互原型
          ↓  delivery-prototype-html
          ↓  产出：可离线运行、可导航、可点击的 prototype/

Step 3   client-gate 客户签字
          ↓  delivery-client-gate
          ↓  产出：客户确认记录.md（A 新签 / B 存量登记 / C 变更确认）

Step 4   架构与技术就绪
          ↓  bmad-architecture / bmad-check-implementation-readiness
          ↓  产出：架构决策 + readiness 报告

Step 5   拆任务进飞书
          ↓  bmad-create-epics-and-stories + delivery-feishu-sync
          ↓  产出：飞书「清单 > 父任务 > 子任务」+ _映射表.json

Step 6   研发实现（从飞书领活）
          ↓  Superpowers（TDD/调试/验证）
          ↓  研发在飞书改「阶段状态」= 开发中 → 测试中 → 已上线
          ↓  delivery-sprint-sync 单向刷新本地 sprint-status.yaml 镜像

Step 7   eval-loop AI 评测
          ↓  delivery-eval-loop
          ↓  产出：评测集.md + 评测报告.md（含门禁结论）

Step 8   测试 / QA
          ↓  人工测试或 bmad-qa-generate-e2e-tests

Step 9   acceptance-gate 客户验收
          ↓  delivery-acceptance-gate
          ↓  产出：验收报告.md（对冻结范围核 KPI/DoD，取客户签字）

完成交付
```

> **硬顺序**：客户签字后，必须先通过架构与技术就绪检查，才能拆任务进飞书。

### 关键纪律

1. **客户没签字 → 不进开发**（client-gate）
2. **技术就绪不达标 → 不拆任务**（architecture + readiness-check）
3. **任务三要素不全 → 不推飞书**（做什么 / DoD / 交付物）
4. **AI 评测 Tier1 不达阈值 → 不进测试/上线**（eval-loop）
5. **没过客户验收 → 不算交付**（acceptance-gate）
6. 需求真源在文档、状态真源在飞书；本地 `sprint-status.yaml` 只是飞书的只读镜像

> 以上关卡是团队共识的流程约定，没有技术强制。但跳过 = 破坏交付可追溯性。
