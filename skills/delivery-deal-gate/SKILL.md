# 合同签约关卡（delivery-deal-gate）

**目标**：BMAD 是内部研发框架，没有乙方↔客户的商务成交环节。本关卡补上流水线最上游这一关——把商机/方案/报价冻结成客户可签约的合同基线，**未签约不放行需求接入**，从源头挡住"没成交就投研发资源"。放行动作产出「立项包」，把商务基线（客户/合同范围/金额/工期/关键约束）喂给下游 SPEC.md 与 project-context.md，PM 起需求时读立项包，不再靠人肉转述——这就是商务与交付之间断层被打通的接缝。

**角色**：你是售前/商务负责人，负责组织合同签约、冻结商务基线、生成立项包移交交付。

## 三关卡对称（本关卡的定位）

```
签约关卡 ─→ … ─→ 范围签字关卡 ─→ … ─→ 验收关卡
deal-gate      client-gate         acceptance-gate
冻结商务基线     冻结需求范围快照      验证交付达标
(合同/金额/工期) (Capabilities 快照)   (对照 DoD)
```

三者是同一段甲乙关系的三层锁：签约锁商务基线、签字锁需求范围、验收锁交付结果。deal-gate 的商机编号（Trace 根）一路传导到 SPEC.md，让全链路可追溯。

## 何时用

在 `delivery-presales` 产出商机档案 + 报价单、客户方决定成交之后、进入需求接入（`requirements`）之前。这是"售前 → 交付"之间的强制关口。

三种入口（与 client-gate 对称）：
- **A 全新签约**：合同还没签 → 组织一次签约并冻结基线（走 step0→1→2→3→4）。
- **B 存量合同登记**：引入本流程前合同已签（往返确认并盖章的合同、中标通知书、已生效 SOW）→ **不重签**，只把已生效合同登记为商务基线（走 step0→1→2→4，跳过 step3 重新组织签约）。避免逼客户重走仪式（KISS）。
- **C 变更确认**：商务基线冻结后，合同金额/范围/工期发生变更（补充协议、变更单）→ 就变更部分回本关卡重新确认（走 step0→1→2→3→4，仅针对变更部分）。不允在交付中静默变更商务基线。

## 输入

- 商机档案（`delivery-presales` 产出，含商机编号 `OPP-{YYYY}-{NNN}` = Trace 根、客户、需求意向）——**立项包的 Trace 根来源**
- `报价单-{date}.md`（`delivery-presales` 产出）——金额/工期/范围的报价依据
- **（A/B 入口）客户已确认的商务材料**（合同、中标通知书、SOW、盖章确认件）——商务基线的事实来源
- 上一版立项包（如有，C 入口用于比对变更）

## 输出

- `合同签约确认记录-{date}.md`（写入交付制品目录，**路径由 project-context.md 或团队约定指定，不硬编码**；未指定则默认 `docs/delivery/`）
  - 内含：商务基线（客户/合同范围/金额/工期/关键约束）、变更清单、签约方式、放行结论
- `立项包.md`（固定名，项目根）——放行时产出的**移交产物**，是商务→交付的接缝：
  - 商机编号（Trace 根）、客户信息、合同范围摘要、预算红线/工期红线、关键商务约束、下游 SPEC/project-context 播种指引
- **写入进度**：更新 `project-progress.yaml`，`deal_gate: done` + `completed_at`，`trace_id` 置为商机编号，`current_stage` 推进到 `requirements`

## 关卡纪律（流程约定，靠自觉不靠技术锁）

> 诚实说明：本关卡是**团队共识约定**，没有程序强制——真人硬跳过直接投研发也没东西拦。但跳过=没成交就投资源、商务基线无法回溯、交付超支扯皮。团队须共识遵守。

1. **合同未签约 → 关卡状态「阻断」**，约定上不进入需求接入。签约可以是本关卡新签（A 入口），也可以是已生效合同的登记（B 入口）——**要点是商务基线有可回溯的成交依据，不是形式**。
2. **商务基线一旦签约即冻结**。之后要改金额/范围/工期：更新立项包、补变更清单、回本关卡**就变更部分重新确认**（C 入口），不在交付中静默变更。
3. 立项包是下游 `delivery-client-gate` 范围快照与 `project-context.md` 预算/工期红线的**上游依据**。范围签字关卡的 Constraints 必须可回溯到本立项包的商务约束。
4. **B 入口只登记既有合同、不伪造签约**。若报价/方案已超出已签合同范围，超出部分按"未签约"处理，退回 A 入口补签或走 C 入口变更。
5. **商机编号 = Trace 根**，一经生成不可变更，赢单后即项目交付编号，贯穿 SPEC/Story/飞书/评测/验收全链路。

<step n="0" goal="判定入口">
  <action>先读商机档案，提取商机编号（`OPP-{YYYY}-{NNN}`）、客户、需求意向——这是后续所有步骤的 Trace 根与商务锚点。若商机档案无编号，回退 `delivery-presales` 先生成。</action>
  <action>问（或从上下文判断）：合同是否**已经**以某种形式签订/生效？</action>
  <action>否 → 走 **A 全新签约**：step1 → 2 → 3 → 4。</action>
  <action>是 → 走 **B 存量合同登记**：step1 → 2 → 4，**跳过 step3**（不再组织重新签约）。要求用户指明已生效合同的**留痕位置与形式**（合同扫描件、中标通知书、SOW）。</action>
  <action>若基线已冻结、本次是变更 → 走 **C 变更确认**：step1 → 2 → 3 → 4，仅针对变更部分。</action>

<step n="1" goal="冻结商务基线">
  <action>读商机档案 + 报价单。A/B 入口下，**同时读取客户已确认的商务材料**（合同/中标通知书/SOW），以其为商务基线的事实来源。</action>
  <action>生成「商务基线」四要素：</action>
  <action>· 客户/甲方 → 单位、签约主体、关键联系人</action>
  <action>· 合同范围 → 逐条列出合同约定的交付范围（每条一句话说清交付什么）</action>
  <action>· 金额/工期 → 合同金额、付款节点、里程碑工期（下游 project-context 预算/工期红线的来源）</action>
  <action>· 关键约束 → 验收标准、违约条款、知识产权、数据合规等对交付有硬约束的条款</action>
  <action>报价单作金额/工期细节依据，合同为准；二者不一致时以已签合同为准，并标出差异。</action>
  <action>若存在上一版立项包，逐条比对，生成「变更清单」（新增/修改/删除 + 原因 + 对范围/金额/工期影响）。</action>
  <check if="A/B 入口">
    <action>核对报价/方案是否与已签合同一致。**若发现报价超出或偏离合同范围**，标出差异——这部分属于"未签约"，需退回补签或走 C 入口变更，不能默认放行。</action>
  </check>
</step>

<step n="2" goal="生成合同签约确认记录 + 立项包">
  <action>按 `templates/合同签约确认记录模板.md` 填写：商务基线、变更清单、签约方式、放行结论。</action>
  <action>按 `templates/立项包模板.md` 生成 `立项包.md`：商机编号（Trace 根）、客户、合同范围摘要、预算红线、工期红线、关键商务约束、下游播种指引。</action>
  <action>立项包的「下游播种指引」明确写清：Why/Constraints/Success signal 三段该怎么喂给 SPEC.md，预算/工期红线该怎么落进 project-context.md。这是移交给 PM 的操作说明，不是空话。</action>
  <check if="B 入口">
    <action>「签约方式」栏登记**已生效合同的形式与出处**（如"合同 v2 双方盖章，{date} 生效"），并附留痕链接/路径。这是登记既有事实，不是补签新字。</action>

  <action>写入交付制品目录（确认记录）与项目根（立项包）。</action>

<step n="3" goal="组织合同签约（仅 A/C 入口）">
  <action>把商务基线发客户方走查，逐条走查合同范围、金额、工期、关键约束。</action>
  <action>记录客户反馈：认可 / 要改 / 有异议。</action>
  <check if="客户要求修改商务条款">
    <action>更新商务基线与变更清单，重新走查，直到双方认可并完成签约动作（盖章/签字/线上签约）。</action>
  </check>
</step>

<step n="4" goal="判定放行">
  <check if="A/C 入口">
    <action>合同完成签约（双方盖章件 / 线上签约留痕 / 中标通知书，注明形式与时间）。</action>
  </check>
  <check if="已签约 或 B入口已登记有效存量合同">
    <action>关卡状态标记「放行」，冻结商务基线。</action>
    <action>**写入进度**：更新 `project-progress.yaml`，将 `deal_gate` 阶段标记为 `done` + `completed_at`，顶层 `trace_id` 置为商机编号，`current_stage` 更新为 `requirements`。若文件不存在，从 `templates/project-progress模板.yaml` 创建（含售前三阶段）。</action>
    <action>提示下一步：PM 读 `立项包.md` 起需求接入，把商务基线播种进 SPEC.md（Why/Constraints/Success signal）与 project-context.md（预算/工期红线），SPEC.md 头部写引用行 `> 商机编号: OPP-YYYY-NNN` 传导 Trace。</action>
    <action if="涉及飞书">用 `delivery-crm-sync` 把商机/合同的「阶段状态」更新为「签约」，保持飞书 CRM SSOT 与本地一致。</action>
  </check>
  <check if="未签约（A 入口）或 存量合同与报价/方案有未消解差异（B 入口）">
    <action>关卡状态标记「阻断」。明确告知：在消解前，不启动需求接入与研发投入。</action>
    <action>记录阻断原因与待客户决策项。</action>
  </check>
</step>

## 与 client-gate 的分工（别混淆两道关卡）

| | deal-gate（本关卡） | client-gate |
|---|---|---|
| 锁什么 | 商务基线：合同/金额/工期 | 需求范围：Capabilities 快照 |
| 位置 | 需求接入**之前**（最上游） | PRD/原型**之后**、架构之前 |
| 依据 | 商机档案 + 报价单 + 合同 | SPEC.md + PRD + 原型 |
| 放行去向 | → 需求接入（requirements） | → 架构（architecture） |
| 产出 | 合同签约确认记录 + 立项包 | 客户确认记录 |

> 一句话：签约关卡管"这单做不做、多少钱、什么工期"；签字关卡管"这单具体做成什么样"。前者的立项包是后者范围快照的上游约束来源。
